# 인증
      
서비스를 이용하는 사용자를 식별하는 기술을 인증(Authentication)이라고 한다. 
   
   
## 1. 인증방식
   
### 01) 계정 정보를 클라이언트에서 저장
- 계정 정보를 클라이언트에서 저장한 후 서버에 보내주는 방식이 있으며 이는 간단한게 구현할 수 있다.
- 웹 브라우저에서는 계정 정보를 쿠키 저장소에 저장하여 인증을 간단하게 구현할 수 있다.
   
#### 쿠키 사용방법
1. 사용자는 로그인 페이지에서 다음처럼 계정 정보를 요청 메세지에 담아 서버에 요청을 보낸다.
```bash
user_id: grab
password: 1234
```
2. 서버는 이 정보를 받아 등록된 사용자임을 확인하고, 응답 메세지에 브라우저 쿠키에 위 정보를 응답 헤더에 인코딩하여 인증 정보를 담는다.
```bash
# 예시 
set-cookie: ajdi3jiorfiosdnfn44..
# 디코딩하게 되면 user_id=12345&password=1234 값을 반환합니다.
```
3. 응답을 받은 클라이언트는 이 데이터를 브라우저 쿠키에 저장한다.
4. 클라이언트는 서버로 요청을 보낼 때 마다 이 쿠키를 함께 보내면, 서버에서는 해당 쿠키 정보를 디코딩해서 데이터베이스를 통해 인증을 진행한다. 
   
이 방법으로 매번 요청에 계정 정보를 담지 않아도 된다.
   
그러나 브라우저의 쿠키에 유저의 인증 정보가 그대로 남아 있다는 점은 보안에 취약하다.   
또한 서버에서는 요청에 포함된 쿠키를 계속해서 데이터베이스와 통신해야하기 때문에 자원 낭비 및 성능 저하로 연결될 수 있다.    
   
#### 쿠키만으로 충분한 경우
딱히 계정 정보와 인증이 필요 없는 경우 쿠키만으로 충분하다.   
대표적으로 쇼핑몰의 장바구니 기능이 있다.    
보통 로그인을 하지 않아도(비회원으로) 장바구니에 물건담기가 가능하다.   
이런 시스템은 별도의 인증을 거치지 않지만, 브라우저에 담긴 쿠키로 개별 회원들을 어느정도 구분한다.   
이렇게 쿠키는 꼭 인증을 목적으로 쓰이지 않고, “임시 저장소”로서 폭 넓게 사용된다.    
      
   
### 02) 세션 기반 인증
   
<img width="820" height="397" alt="Image" src="https://github.com/user-attachments/assets/d5fd9913-26ad-4998-8bab-a3e412891223" />
   
세션은 클라이언트와 서버 간의 네트워크 연결에 대한 정보를 담고 있는 객체이다.   
보통 인증을 구현할 때 인증 정보를 담을 수 있는 세션을 많이 활용한다 .   
   
1. 사용자는 쿠키를 사용하는 때와 똑같이 로그인 페이지에서 계정 정보를 다음처럼 요청 메시지에 담아 서버에 요청을 보낸다.
```bash
user_id: grab
password: 1234
```
2. 서버는 이 계정 정보를 받아 유효한 계정인지 확인한 후, “세션” 이라고 하는 객체를 만들어 유저 정보와 접속 시간 등 연결에 대한 정보를 이 객체에 담는다. 그리고 세션을 세션 저장소에 저장한다. 
3. 그리고 응답 헤더에 생성한 세선 ID를 담아 클라이언트에게 응답한다.
```bash
# 예시 
set-cookie: sessionid=12345
```
4. 응답을 받은 클라이언트는 이 데이터를 마찬가지로 브라우저 쿠키에 저장한다.
5. 클라이언트와 서버는 그대로 드러나는 세션 ID를 주고받게되고, 서버는 요청을 받을 때 마다 세션 저장소에서 세션 ID를 찾고, 유효한 세션인지 확인한다. 만약 유효하다면 인증에 성공하고 유효하지 않는다면 인증에 실패한다. 
   
#### 세션기반인증의 장점
- 계정 정보를 브라우저의 쿠키에 그대로 노출하지 않는다.
- 세션의 유효기간을 설정할 수 있기에 보안과 다양한 기능(동시 접속 차단 등)을 구현할 수 있다.
- 데이터베이스의 부하를 줄일 수 있다. 
   
다만 인증에 필요한 데이터들을 서버 혹은 별도의 세션 서버에 관리하기 때문에 서버에 부하가 생기게 된다.   
실제로 대규모 서비스를 운형하기 위해선 세션 저장소를 체계적으로 관리하는 일도 중요하다.    
   
   
### 03) 토큰 기반 인증
   
<img width="820" height="382" alt="Image" src="https://github.com/user-attachments/assets/80bc77ec-19a4-425a-a4f7-1b0e1dab2a8c" />   
   
세션 방식과 함께 많이 사용되는 인증 방식으로 토큰인증(Token Authentication) 방식이 있다.   
토큰은 별도의 저장소를 사용하지 않고, ‘토큰’이라고 하는 하나의 문자열에 인증에 필요한 데이터를 모두 담는 방식이다.    
토큰은 여러 종류가 있으나, JWT(Json Web Token)이 가장 흔하게 사용된다.    
   
토큰을 사용하는 방법은 다음과 같다.    
   
1. 사용자는 로그인 페이지에서 계정 정보를 다음처럼 요청 메세지에 담아 서버에 요청을 보낸다.
```bash
user_id: grab
password: 1234
```
2. 서버는 이 계정 정보를 받아, 유효한 사용자인지 확인한 후 다음처럼 유저 정보와 인증에 필요한 대이터를 문자열로 암호화한다. (이 문자열을 토큰이라고 한다(이 문자열을 토큰이라고 한다.)
```bash
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```
      - 토큰은 인증에 필요한 정보를 담아 암호화된 문자열인데, 이 문자열을 복호화하면 원본 데이터를 얻을 수 있다. 
```bash
user_id: grab
role: Admin
created_at: 2021-08-11 18:32:01
```
3. 서버는 응답 메시지에 위 토큰을 담아 응답하고 클라이언트는 해당 토큰을 특정 저장소에 저장한다. 
4. 클라이언트가 토큰을 포함하여 요청을 했을 때, 서버에서는 토큰을 복호화하여 사용자를 확인한다. 만약 올바르지 않은 위변조된 토큰이라면 복호화하지 않는다. 
   
이 방법은 세션처럼 별도의 세션 저장소가 필요하지 않아 상대적으로 구현이 간편하다.    
인증로직(토큰 암호화와 복호화)을 서버에 잘 구현해두면 된다.    
   
하지만 토큰이 많은 데이터를 저장할수록 토큰이 커지면서 네트워크 통신 비용이 비싸진다.   
한번 발급된 토큰에 대해서는 중간에 폐기할 수 없다는 단점도 존재한다.    
   
#### TIP
결국 세션과 토큰 방식의 차이는, 세션은 별도의 저장소에서 세션들을 관리하고 대조하는 방식이며   
토큰은 암호화,복호화 방식으로 별다른 저장소 없이 인증을 진행하는 방식이다.     
   
   
## 2. 인가
인가(Authorization)는 인증을 마친 사용자가 요청에 대해 유효한 권한이 있는지를 확인하는 작업이다.    
예를들어 게시판에서 일반 계정은 자신의 글만 수정하고 지울 수 있다.   
하지만 관리자 사용자는 모든 계정의 글을 수정하고 지울 수 있는 권한이 있다.   
이처럼 인증된 계정 사이에도 “권한”이 다른 경우가 있다.   
그래도 어떤 자원에 대해 접근을 사용자 권한(Role)에 따라 다르게 설정해주는 것이 중요하다.    
   
   
## 3. 정리
- 인증은 사용자가 등록된 사용자인지 확인하고 식별하는 작업이다.
- 현대에는 인증 방식으로 세션, 토큰방식을 많이 사용한다.
- 세션 인증 방식에는 세션이라는 객체로 인증하는 방식으로, 세션 ID를 헤더에 담아 클라이언트/서버가 주고받는다. 세션을 직접 관리하기에 다양한 인증 처리(동시접속차단, 유저트래킹)를 구현할 수 있다.
- 토큰 인증 방식은 유저 정보를 토큰이라고 하는 암호화된 문자열로 만들어 이를 주고받으며 인증하는 방식이다. 별다른 저장소가 필요하지 않기에 서버를 스케일 업해도 문제가 되지 않는다.
- 인가는 인증이 완료된 사용자가 요청에 대해 유효한 권한을 가지고 있는지 확인하는 작업이다.
