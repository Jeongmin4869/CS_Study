## 03 - 함수
      
### 01) 함수의 역할은 하나만 할 수 있도록 한다 (SRP)
- 함수의 역할이 많아지면 오류가 날 가능성이 커지며 가독성이 떨어진다.
- 함수에 대한 테스트를 진행하기 어려워진다. 
   
as-is
``` python 
def create_user(email, password):
    # validation 로직
    if "@" not in email or len(password) < 6 :
        raise Exception("유저 정보를 제대로 입력하세요")

    user = {"email" : email, "password" : password}
    
    database = Database("mysql")
    database.add(user)
    
    email_client = EmailClient()
    email_client.set_config(...)
    email_client.send(email, "회원가입을 축하합니다")

    return True

   
```
   
to-be
``` python 
def create_user(email, password):
    validate_create_user(email, password)

    user = build_user(email, password)
    
    save_user(user)
    send_email(email)
    return

def validate_create_user(email, password):
    if "@" not in email or len(password) < 6 :
        raise Exception("유저 정보를 제대로 입력하세요")

def build_user(email, password):
    return {
        "email": email,
        "password": password
    }

def save_user(user):
    database = Database("mysql")
    database.add(user)

def send_email(email):
    email_client = EmailClient()
    email_client.set_config(...)
    email_client.send(email, "회원가입을 축하합니다")

```

### 04) 사이드 이팩트를 잘 핸들링한다.
- 사이드 이팩트는 함수가 실행됐을 때 함수 외의 다른 것들에 영향을 주는 것을 의미한다.
- 사이드 이펙트를 잘 다루지 못하면 예상치못한 문제들이 발생할 수 있다. 
   
```python 
#사이드 이펙트가 없습니다.
def get_user_instance(email, password):
    user = User(email, password)
    return user
	
#사이드 이펙트가 있습니다
def update_user_instance(user): 
    user.email = "new email" #인자로 받은 user 객체를 업데이트합니다.
    ...

#사이드 이펙트가 있습니다
def create_user(email, password):
    user = User(email, password)
    start_db_session() #외부의 DB Session에 변화를 줄 수 있습니다. 
    ...

```
   
### 사이드 이펙트 핸들링
- 1. 코드를 통해 충분히 기능을 예측할 수 있도록 네이밍한다.
  - Update, set 같은 직관적인 preifx를 붙여 사이드 이펙트가 있을 수 있음을 명시한다. 
- 2. 함수의 사이드 이펙트가 있는 부분과 없는 부분으로 잘 나눠 관리한다.
   - 명령(side effect O)과 조회(side effect X)를 분리하는 CQRS 방식이 있다.
- 3. update문을 남발하기 보다는 순수 함수 형태로 사용하는 것이 더 직관적이며 에러를 방지할 수 있다.
   
as-is
```python
carts = []

#사이드 이펙트를 발생시킴
def add_cart(product):
    carts.append(product)

product = Product(...)
add_cart(product)

```
   
to-be
```python
carts = []

#사이드 이펙트가 없는 순수함수
def get_added_cart(product):
    return [...carts, prodcut]

product = Product(...)
carts = get_added_cart(product)

```

### 02) 응집도 높이기 
- 응집도는 클래스의 변수와 메서드들이 얼마나 유기적으로 엮어있냐를 나태는 지표이다.
- 응집도가 높을수록 클래스의 메서드들은 인스턴트 변수들을 많이 사용한다.
- 응집도가 낮을수록 클래스의 매서드들은 인스턴트 변수들은 적게 혹은 아예 사용하지 않는다.
   
as-is
```python
class LowCohesion:
    def __init__(self):
        self.a = ...
        self.b = ...
        self.c = ...

   # 각각의 메서드들은 인스턴트 변수들을 하나씩만 사용중
    def process_a(self):
        print(self.a)

    def process_b(self):
        print(self.b)

    def process_c(self):
        print(self.c)

```
   
to-be
```python

class HighCohesion:
    def __init__(self):
        self.abc = ...

    def process_a(self):
        self.abc.process_a()

    def process_b(self):
        self.abc.process_b()

    def process_c(self):
        self.abc.process_c()

```
   
      
### 03) 변경에 용이한 클래스 
- 새 기능을 수정한거나 기존의 기능을 변경할 때 코드의 변경을 최소화해야한다.
- 클래스는 구현과 추상으로 나뉘며, 구현에는 실제 동작하는 코드가,  추상은 인터페이스나 추상 클래스처럼 기능을 개념화한 코드가 들어간다.
- 변경하기 쉽게 설계하기 위해선 추상화를 해두고 구체 클래스의 의존하지 않고 추상 클래스(인터페이스)에 의존하도록 코드를 짜는 것이 중요하다. 
   
as-is
```python
class Developer:
    def coding(self):
        print("코딩을 합니다")

class Designer:
    def design(self):
        print("디자인을 합니다")

class Analyst:
    def analyze(self):
        print("분석을 합니다")

class Company:
    def __init__(self, employees): #구체 클래스에 의존합니다. 
        self.employees = employees

    # employee가 다양해질수록 elif가 늘어나며, 코드를 계속 변경해야한다. 
    def make_work(self):
        for employee in self.employees:
            if isinstance(employee, Developer):
                employee.coding()
            elif isinstance(employee, Designer):
                employee.design()
            elif isinstance(employee, Analyst):
                employee.analyze()

```
   
to-be
```python
class Employee(metaclass=abc.ABCMeta):
    @abc.abstractmethod
    def work(self):
        ...

class Developer(Employee):
    def work(self):
        print("코딩을 합니다")

class Designer(Employee):
    def work(self):
        print("디자인을 합니다")

class Analyst(Employee):
    def work(self):
        print("분석을 합니다")

#상속을 통해 쉽게 구현이 가능함 -> 확장에 열려있다.
class Manager(Employee):
    def work(self):
		print("매니징을 합니다")

class Company:
    def __init__(self, employees: List[Employee]): #추상 클래스에 의존합니다.
        self.employees = employees

    # employee가 늘어나더라도 변경에는 닫혀있다.
    def make_work(self):
        for employee in self.employees:
            employee.work()
```

```python
class CustomException(Exception):
    ...

class WithParameterCustomException(Exception):
    def __init__(self, msg, kwargs):
        self.msg = msg
        self.kwargs = kwargs

raise WithParameterCustomException("문제가 있습니다", {"name": "grab"})
```


```python
def say_hi_to_spring_user(developer):
```

to-be
```python
def say_hi_to_spring_user(developer):
    if developer.is_front_end:
        raise Exception("프론트 엔지니어입니다")
```
