# 5. 객체지향프로그래밍 기본 

## 프로그래밍 패러다임
- 프로그래밍 패러다임은 프로그래밍할 때 환경을 제공해 주고, 설계를 결정하도록 돕는 패러다임이다. 
- 함수적 호출 과정을 숭심으로 바라보고 설계한다면 절차지향 프로그래밍
- 객체의 채깅ㅁ과 협력을 중심으로 설계한다면 객체 지행 프로그래밍이 된다.
- C언어는 대표적인 절차지향 언어이며, 자바는 대표적인 객체지향 언어이다.
- 파이썬은 두 패러다임을 모두 수용하는 멀티 패러다임 언어이다. 
   
### 3가지 프로그래밍 패러다임
- 절차지향 프로그래밍
- 객체지향 프로그래밍
- 함수지향 프로그래밍 

--- 
### 01. 절차지향 프로그래밍 
- 절차지향(Procedure Oriented) 프로그래밍은 프로시저 콜, 즉 함수 호출을 중심으로 프로그래밍을 생각하는 것이다.
- 재사용가능한 코드들은 별도의 함수로 분리하고, 함수간의 호출로 하고자하는 일을 수행한다.
- 이러한 프로세스는 주로 함수와 조건문, 루프문을 활용하여 코드를 구성한다.
- 절차지향 프로그래밍은 데이터를 중앙 집중식으로 관리한다.
- 프로세스 로직과 데이터가 별도의 위치에 분리되어있다.
- 프로세스 로직 부분에서는 어떤 데이터가 들어오는지 모르기 때문에 로직 내에 조건문 사용이 많은 경향이 있따.
   
#### 예시) 절차지향 프로그래밍으로 짠 파이썬 코드 
- main 함수는 하위 함수들의 호출로 이루어져 있따.
- main함수만 보면 프로그램 로직을 쉽게 파악할 수 있다.
- 절차지향 코드는 이렇게 전체 로직을 작은 함수 단위로 나누고 프로그램 메인 로직이 시작되는 곳부터 하위 로직이 실행되는 곳 까지 TOP-DOWN식으로 구성된다 .
 
```python

def read_input_file(file_path: str) -> str:
    if file_path.endswith(".txt"):
        reader = get_file_reader(file_type="txt")
        return reader.read(file_path)

    else:

    if file_type == "txt":
   		...
    elif file_type == "csv":
        ...
    elif file_type == "xlsx":
        ...

def parse_input_data(data: str) -> List[str]:
    ...

    ...
``` 

### 02. 객체지향 프로그래밍
- 객체지향(Object Oriented)프로그래밍은 객체라고 하는 단위의 책임을 명확히하ㅏ고 서로 협력하도록 프로그래밍하는 패러다임이다.
- 모든것을 객체로 나누어 생각하고, 필요할 때 객체들을 활용하고 서로 협력하여 일을 수행한다.
- 절차지향과는 다르게 객체는 데이터와 함수(메서드)를 함께 가지고 있다.
- 객체 내부의 데이터는 외부에 공개할 필요가 없거나 해서는 안되는 데이터라면 모두 자신 내부에 숨겨 외부에서 알지 못하도록 한다. 
   
```python
class Processor:
    def __init__(self,
                 file_reader: FileReader,
                 data_parser: DataParser,
                 repository: Repository) -> None:
        self.file_reader = file_reader
        self.data_parser = data_parser
        self.repository = repository

    def execute(self, file_path: str) -> None:
        data = self.file_reader.read(file_path)
        parsed_data = self.data_parser.parse(data)
        self.repository.save(parsed_data)


class FileReader:
    def __init__(self) -> None:
        self.file_types = ["txt"]
        self.file_history = [] # 만약 절차 지향이라면 file_history 데이터를 중앙 집중으로 관리하게 됩니다. 

    def read(self, file_path: str) -> str:
        self._validate(file_path)
        ...

    def _validate(self, file_path: str) -> None:
        for file_type in self.file_types:
            if file_path.endswith(file_type):
                return
        raise ValueError("파일 확장자는 txt, csv, xlsx 중 하나여야 합니다.")

class DataParser:
    def parse(self, data: str) -> List[str]:
        ...

class Repository:
    def init(self, database_url: str, ...):
        ...
    
    def save(self, data: List[str]) -> None:
        ...

class Main:
    @staticmethod
    def run(self) -> None:
        processor = Processor(
            file_reader=FileReader(),
            data_parser=DataParser(),
            repository=Repository()
        )
        processor.execute("input_file.txt")


 if __name__ == "__main__":
    Main.run()

``` 
   
- 코드는 Processor, FileReader 등 여러 객체(문법으로는 클래스)로 이루어진다.
- 각 객체는 자신의 역할과 기능이 있다. FileReader는 파일을 읽고, DataParser는 데이터를 파싱한다.
- 프로그래밍은 전체적으로 객체와 객체간의 메서드 호출로 이루어진다.
- 각 객체는 자신의 기능을 수행하는데 필요한 데이터를 직접 가지고 았다. (FileReader는 file_types속성으로 파일 확장자를 검증한다)
   
- 코드는 조금 더 복잡해졌지만 객체지향은 기능을 확장할 때 효과적이다. 
   
```python
# FileReader는 이제 추상 클래스입니다.
class FileReader(ABC):
    def read(self, file_path: str) -> str:
        self._validate(file_path)
        data = self._open_file(file_path)
        return self._read(data)

    @abstractmethod
    def _read(self, data: str) -> str:
        pass

    # 공통으로 사용하는 메서드입니다.
    def _validate(self, file_path: str) -> None:
        if not file_path.endswith(self.file_type):
            raise ValueError(f"파일 확장자가 {self.file_type} 아닙니다.")

    @abstractmethod
    def _open_file(file_path: str) -> str:
        ...

# txt 파일을 읽는 책임을 가진 FileReader 파생 클래스입니다.
class TxtFileReader(FileReader):
    def file_type(self) -> str:
        return "txt"

    def _read(self, data: str) -> str:
        ...
    
    ...


# csv 파일을 읽는 책임을 가진 FileReader 파생 클래스입니다.
class CsvFileReader(FileReader):
    def file_type(self) -> str:
        return "csv"

    def _read(self, data: str) -> str:
        ...
    
    ...


# xlsx 파일을 읽는 책임을 가진 FileReader 파생 클래스입니다.
class XlsxFileReader(FileReader):
    def file_type(self) -> str:
        return "xlsx"

    def _read(self, data: str) -> str:
        ...

    ...

``` 
   
- 객체지향을 지원하는 프로그래밍 언어는 클래스라는 문법을 제공한다.
- 객체의 강력한 기능인 상속을 이요하면 한 번 정의해놓은 메서드들을 파생 클래스에서 재사용 가능하다. 
- 상속으로 객체간의 계층 구조를 만들고 데이터와 메서드를 재사용할 수 있다.
   
- 객체지향의 가장 큰 특징은 같은 역할을 하는 객체를 쉽게 바꾸로도록 설계할 수 있다는 점이다. 
   
```python
class Main:
    def run(self) -> None:
        processor = Processor(
            file_reader=TxtFileReader(),
        	data_parser=DataParser(),
            repository=Repository()
        )

```
   
- cvs나 xlsx파일을 읽어야 할 경우 아래처럼 한 줄만 바꾸면 된다 
   
```python
class Main:
    def run(self) -> None:
        processor = Processor(
            file_reader=CsvFileReader(), # 이 한줄만 바뀌게 된다 
        	data_parser=DataParser(),  
            repository=Repository()
        )

```
      
- 한줄만으로 가능한 이유는 TxtFileReaer와 CvsFileReser가 모두 FileReader의 파생 클래스이기 때문이다. 
- 이런 객체 지향의 특성을 다형성이라고 하며, 어떤 객체에 필요한 객체를 때에 따라 다르게 주입해주는 것을 “의존성 주입” 이라고 한다. 
   
   
#### 장단점
- 여러명의 개발자들이 협력을 해야하거나 확장 가능하도록 코드를 설계해야하는 경우에 적합하다
- 확장이 가능하고 유연한 만큼 코드를 처음 보는 사람은 어렵고 헷갈릴 수 있다. 
- 실행 환경에서 입력에 따라 다양한 작업흐름이 만들어지기 때문에 디버깅하기가 상대적으로 어렵다.

### 03. 함수 프로그래밍 
   
#### 기존 객체지향 프로그래밍에서 가지는 문제
- 함수의 비일관성 : 객체의 멤버 변수가 변경될 경우 함수(메소드)가 다른 결과를 반환할 수 있다.
- 객체간 의존성 문제 : 객체 간 상호작용을 위해 다른 개게의 함수들을 호출하게 되고, 이는 프로그램 복잡도를 증가시킨다.
- 객체 내 상태 제어의 어려움 : 외부에서 객체의 상태를 변경하는 메소드들이 호출될 경우, 언제 어디서 객체의 상태를 변경했는지 추적이 어렵다
   
#### 함수 프로그래밍 	
- 함수형 프로그래밍(Functional) 은 외부 상태를 갖지 않는 함수들의 연속으로 프로그래밍을 하는 패러다임이다.
- 외부상태를 갖지 않는다는 의미는, 같은 입력을 넣었을 때 언제나 같은 출력을 내보낸다는 것을 의미한다.
- 함수의 입/출력에 영향을 주는 외부 요인이 없다.
- 함수형 프로그래밍에서는 한 번 초기화한 변수는 변하지 않는다. 이런 특성을 불변성이라고 하며 이를통해 안정성을 얻을 수 있다. 
   
#### 기본개념
- 함수형 프로그래밍에서는 함수가 외부 상태를 갖지 않는다는 것이 중요하다.
- 외부상태를 갖지 않는 함수를 순수함수 라고 한다. 
   
```python

# 순수함수 아님

c = 1

def func(a: int, b: int) -> int:
    return a + b + c  # c 라는 외부 값, 상태가 포함되어 있기에 함수형이 아닙니다.

```
   
```python

# 순수함수

def func(a: int, b: int, c: int) -> int:
    return a + b + c  # 주어진 파라미터만 사용합니다. 별도의 상태가 없습니다.


```
   
- 함수형 프로그래밍은 같은 입력을 주었을 때 항상 같은 값을 출력하도록 상태를 갖지 않는다.
- 통제하지 못하는 외부상태를 사용한다면 예측하지 못한 결과를 가질 수 있다.
- 매번 상태를 가질 경우 같은 함수를 실행하더라도 실제로 의도하는 결과가 나오는지 단언하기 어렵다.
- 상태는 어디서든 바뀔 수 있으며 이런 현상을 사이드이펙트 라고 한다.
- 객체지향언어는 이러한 문제를 해결하기 위해 접근제어자(private, protected)와 같은 기능을 제공하지만, 완벽한 해법이 되지는 않는다. 
   
```python

class Calculator:
    def __init__(self, alpha: int) -> None:
        self.alpha = alpha
        self.beta = 0

    def run() -> int
    	return self.alpha + self.beta


calculator = Calculator(alpha=3)
calculator.run()  # 3 반환
calculator.beta = 1
calculator.run()  # 4 반환

```
   
   
#### 예시 
- 1. 함수형 프로그래밍은 다음과 같은 순서로 문제를 해결한다.
- 2. 문제를 잘게 쪼갠다.
- 3. 쪼개진 문제들 중 하나를 해결하는 순수함수를 만든다.
- 4. 순수 함수들을 결합하여 문제들을 해결한다. 
   
- 보통 함수형 프로그래밍에서는 함수를 조합하는 방식으로 Pipelining, Partial, Application, Currying 등이 있다.
- 프로그래밍 언어 중에서는 대표적으로 스칼라(Scala)가 함수형 프로그래밍을 따르는 언어미여, 다른 프로그래밍 언어에서도 특정 API를 사용하면 함수형 프로그래밍이 가능해진다. 
   
```python
# Pipelining
def main():
    pipe_func = pipe(read_input_file, parse_input_data, save_data)
    return pipe_func("input_file.txt")


# Partial application
def power(base, exp): #powering
    return base ** exp

def main():
    square = partial(power, exp=2)
    cube = partial(power, exp=3)
    square(2) #2의 제곱인 4 반환
    cube(2) #2의 세제곱인 8 반환

```
   
#### 장단점
- 함수형 프로그래밍은 상태로 인한 이펙트가 없어 안정적이다.
- 동시성을 가지는 프로그램에 사용하기 적합하다
- 대용량 데이터를 병력적으로 처리할 때 사이드 이펙트가 없도록 로직을 설계하는것이 매우 중요하며, 최즌 데이터 처리기술의 발전으로 함수형 프로그래밍이 부상되었다.
- 실제로 함수형 프로그래밍을 하기 위해선 상태를 허용하지 않기에 기존 객체 지향과 같은 기능의 코드를 구현하려면 다향한 함수들을 조합하여 사용해야한다.
- 진숙하지 않은 방식으로 인해 러닝 커브가 높다

### 정리
- 프로그래밍 패러다임은 프로그래밍을 어떤 기준으로 바라보고 작성할 것인지에 관한 관점이다.
- 절차지향 프로그래밍은 순차적인 함수 호출 중심의 관점이다.
   - 주로 구조가 TOP-DOWN이며, 소스를 이해하기 쉽다
   - 코드를 확장하거나 자주 실행에 따라 로직이 바뀌어야 하는 경우 수정하기 어렵다
- 객체 지향 프로그래밍은 객체들의 책임과 협력 중심의 관점이다.
   - 다형성과 의존성 주입으로 코드를 확장하기 쉬우며, 실행환경의 다양한 입력에 대응하기 좋다
   - 런타임이 되기 전에 실제로 코드아 어떤 방향으로 흐르는지 알기 어려우며, 디버깅이 어렵다. 
- 함수형 프로그래밍은 상태를 갖지 않는 함수들의 활용 중심의 관점이다. 
  - 상태를 가지지 않기 때문에 예측에서 벗어나는 결과가 없다
  - 실제로 상태를 가지지 않는 함수를 작성하고 활용하는 코드를 작성하는 것은 어렵다.

### 04. - 객체지향의 기본적 개념
   
#### 01) 클래스와 인스턴스
   
#### 클래스
- 객체 지향을 지원하는 대부분 프로그래밍 언어에서는 객체 구현을 위해 클래스를 지원한다.
   
```python
# 아무 내용이 없는 비어있는 클래스
class User:
    pass  

``` 
   
#### 인스턴스
- 클래스를 하나의 인스턴스로 만들수 있다. (클래스에 의해 생성된 객체)
- 이를 클래스를 인스턴스화 한다고 한다.
- user_1과 user_2는 같은 클래스로부터 만들어졌지만 서로 다른 인스턴스이다.
- 둘은 같은 형태(클래스)를 취하고 있지만 각자 다른 메모리 공간에 존재하고, 각자 독립된 내용을 담을 수 있다. 
   
```python
>>> user_1 = User()
>>> user_2 = User()

>>> user_1 == user_2
False

```
   
   
#### 02) 속성과 메서드
   
#### 속성
- 클래스의 속성(attribute)은 클래스 내에 담기는 데이터를 말하고 멤버변수라고도 이야기한다.
- 클래스의 속성은 크게 클래스 변수와 인스턴스 변수로 나눌 수 있다.

##### 인스턴스 변수
- 인스턴스 변수는 인스턴스별로 독립적으로 가질 수 있는 값이다.
- 인스턴스변수는 아래 코드처럼 인스턴스별로 다르게 설정할 수 있다.
- 인스턴스 변수는 인스턴스명에 . 를 붙여 접근할 수 있다. 
   
```python
class User:
    def __init__(self, name: str, job: str) -> None:
        self.name = name
        self.job = job

user_1 = User(name="grab", job="data_engineer")
user_2 = User(name="heumsi", job="project_manager")

>>> user_1.name
grab
>>> user_1.job
data_engineer

``` 
      
##### 클래스 변수
- 클래스변수는 클래스 자체에 정의되는 변수이다.
- 같은 클래스의 인스턴스들은 같은 클래스 변수값을 가지게 된다.
- 클래스도 인스턴스변수와 마찬가지로 클래스명에 . 을 붙여 접근할 수 있다.
- 인스턴스별로 독립된 메모리 공간을 가지는 인스턴스변수와 달리, 클래스 변수는 같은 클래스의 인스턴스들이 공유한다. 
   
```python
class User:
    num_users: int = 0
    
    def __init__(self, name: str, job: str) -> None:
        self.name = name
        self.job = job
        User.num_users += 1

# 클래스 변수는 인스턴스화 하지 않아도 접근이 가능합니다.
>>> User.num_users
0

# 인스턴스화한 후에도 접근이 가능합니다.
>>> user_1 = User(name="grab", job="data_engineer")
>>> user_1.num_users
1

# 서로 다른 인스턴스더라도 클래스 변수는 공유됩니다.
>>> user_2 = User(name="heumsi", job="project_manager")
>>> user_2.num_users
2

``` 
   
   
#### 매서드
- 메서드는 클래스가 가지고 있는 함수이자 객체가 할 수 있는 행위를 말한다.
- 메서드는 크게 공개형(public)과 비공개형(private)메서드로 나눌 수 있다
   
##### 공개형 메서드
- 공개형 메서드는 이 클래스가 외부에 제공해주는 메서드이다. 
```python
class User:
    def __init__(self, name: str, job: str) -> None:
        self.name = name
        self.job = job
    
    def work(self) -> None:
        if self.job == "data_enginner":
            print("데이터 엔지니어링 관련된 일을 합니다.")
        elif self.job == "project_manager":
            print("프로젝트 매니징 관련된 일을 합니다.”)


>>> user_1 = User(name="grab", job="data_engineer")
>>> user_1.work()

"데이터 엔지니어링 관련된 일을 합니다."

``` 
   
##### 비공개형 메서드
- 비공개형 메서드는 클래스 내부에서만 사용하는 메서드이다.
- 파이썬의 경우 자바와 다르게 접근 제어자 문법이 없다.
- 다만 변수나 메서드 이름 앞에 _ 를 붙임으로써 비공개 변수, 메서드임을 명시하는게 관습이다.
- __를 두개 붙여 좀더 private하게 변수나 메소드를 관리할 수 있는 name mangling도 있다
- 비공개형 메서드는 외부에서 접근하지 못하거나, 할 수 있더라도 하지 않는게 관습이다.
- 비공개형 메서드는 공개형 메서드의 로직의 일부를 내부적으로 재사용하고, 의미를 분리하기위한 목적으로 사용하곤 한다. 
   
```python
class User:
    def __init__(self, name: str, job: str) -> None:
        self.name = name
        self.job = job
    
    def work(self) -> None:
        work_type = self._get_work_type()
        print(f"{work_type} 관련된 일을 합니다.")
            
    def _get_work_type(self) -> str:
        if self.job == "data_enginner":
            return "데이터 엔지니어링"
       	elif self.job == "project_manager":
            return "프로젝트 매니징"

```
   
##### 접근제어자
- 접근 제어자는 변수 혹은 함수(메서드)에 대한 접근을 제어하는 역하을 한다.
- 자바와 같은 객체지향 언어에는 private, public, protected와 같은 접근 제어자가 있다.
- private로 표시된 변수나 메서드는 클래스 내부에서만 접근할 수 있다.
- 클래스 외부에서 접근하려고 시도할 경우 컴파일 시점에 에러를 뱉는다.
- 객체 지향 언어에서는 보통 이런 제어자를 통해 공개형, 비공개형에 대한 표시를 명확히 한다. 
   
   
#### 03) 상속
- 객체 지향 프로그래밍 언어들은 대부분 클래스의 문법과 상속을 제공한다.
- 상속(inheritance)는 이전에 정의한 클래스의 데이터와 메서드를 그대로 내려받는 기능이다.
- 상속해주는 클래스를 ‘부모 클래스’, ‘기반클래스’ 라고 하며
- 상속받는 클래스를 ‘자식클래스’, ‘파생 클래스’ 라고 한다.
   
```python
class Job:
    def do(self) -> None:
        print(f"{self.work_type} 관련된 일을 합니다.")
    
    
class DataEnginner(Job):
    work_type = "데이터 엔지니어링"
    
    
class ProjectManager(Job):
    work_type = "프로젝트 매니징"
```
   
- DataEngineer, ProjectManager 클래스는 Job클래스를 상속받았다.
- Job클래스는 부모클래스, DataEngineer, ProjectManager는 자식클래스이다.
- DataEngineer, ProjectManager 클래스는 Job을 상속받았으므로 Job클래스에서 정의한 do(self)메서드를 사용할 수 있다. 
   
```python 
>>> data_enginner = DataEnginner()
>>> data_enginner.do()

"데이터 엔지니어링 관련된 일을 합니다."
```
   
   
#### 04) 인터페이스
   
##### 인터페이스
- 인터페이스(interface)는 객체의 행위(메서드)만을 정의한 것이다.
- 파이썬에서는 인터페이스가 따로 없어 추상클래스로 인터페이스를 구현할 수 있다
   
```python
from abc import ABC, abstractmethod

class Job(ABC):
    @abstractmethod
    def do(self) -> None:
        pass

```
   
##### 구현체
- 인터페이스는 보통 그대로 인스턴스화 할 수 없다. 
   
```python
>>> job = Job()

Traceback (most recent call last):
File "<stdin>", line 1, in <module>
TypeError: Can't instantiate abstract class Job with abstract methods do

```
   
- 인터페이스는 객체의 뼈대만을 담당하고있다. 실제는 인퍼테이스 객체를 상속받는 구현 클래스도 구현해야한다. 
   
```python
class DataEngineer(Job):
    def do(self) -> None:
        print("데이터 엔지니어링 관련된 일을 합니다.")

class ProjectManager(Job):
    def do(self) -> None:
        print("프로젝트 매니징 관련된 일을 합니다.")

```
   
```python
>>> data_engineer = DataEngineer()
>>> data_enginner.do()

"데이터 엔지니어링 관련된 일을 합니다."
```
   
##### 인터페이스 사용 이유 
- 특정 행위를 하기위해 구체적으로 어떤 알고지름을 가지고있는지 클라이언트 입장에서는 중요하지 않다.
- 우리는 Job이 어떤 행위를 제공하는지 보려면 그저 Job이라고 하는 인터페이스만 보면 된다.
- 그렇게 되면 자연스럽게 구현(저수준 코드)를 의존하기보단 인터페이스(고수준)에 의존하게 되어 결합도를 낮출 수 있다 -> 다형성
- DataEngineer(Job), ProjectManager(Job)과 같은 구현 클래스가 Job추상 클래스를 상속받는것을 통해 이 두 클래스가 같은 개념 아래 묶여있는 것을 알 수 있다.
- 구현 클래스 간의 관계를 파악하기 쉬워진다. 
   
   
#### 05) 추상클래스 (abstract class)
   
- 추상클래스란 미구현 추상메서드를 한개 이상 가지며, 자식클래스에서 해당 추상 메소드를 반드시 구현하도록 강제한다.
- 상속받은 클래스는 추상메서드를 구현하지 않아도, import 할 때까지 에러는 발생하지 않으나, 객체 새성시 에러가 발생한다.
- 추상 클래스를 만들기 위해서는 abc 모듈을 import 해야한다. 
   
```python
from abc import *
class 추상클래스명(metaclass=ABCMeta):

     @abstractmethod
        def 추상메소드(self):
            pass

```
   
   
### 05 - 객체지향의 특성
   
#### 01) 책임과 협력
   
##### 책임(Responseibility)
- 책임은 한 객체가 특정하게 수행해야하는 범위와 기능을 말한다.
- 사람 객체는 운전하는것에 대한 책임이 있다.
- 차량이라는 객체는 가속과 감속에 대한 책임이 있다
   
```python
class User:
    def __init__(self) -> None:
        pass

    def drive(self) -> None:
        pass

class MorningCar:
    def __init__(self) -> None:
        pass

    def accelerate(self) -> None:
        pass

    def decelerate(self) -> None:
        pass
```
   
##### SRP(Single Responsibility Principle)
- 하나의 객체는 하나의 책임만 가지도록 설계하는것이 좋다
- 객체의 정체성이 명확하고 변경에 용이
- 재사용 가능
- 높은 응집도와 낮은 결합도를 유지
   
   
##### 협력
- 사람이 운전하는 상황은 결과적으로 User객체와 MorningCar객체를 각자 책임에 맞게 설계하고 User가 MorningCar객체를 호출하여 구현해냈다.
- 객체가 서로 필요에 따라 의존하는것을 협력이라고 한다. 
   
```python
class User:
    def __init__(self) -> None:
        self.car = MorningCar()  # User는 MorningCar를 의존하고 있습니다.

    def drive(self) -> None:
        self.car.accelerate()  # User는 MorningCar가 제공하는 공개 메서드를 사용합니다.

class MorningCar:
    def __init__(self):
         self.speed = 0 
         self._fuel = 0  # 파이썬 특성상 private을 _ prefix를 붙여 암묵적으로 사용함
						
    def accelerate(self):
        self.speed += 1

    def decelerate(self):
        self.speed -= 1

```
   
   
##### 책임주도설계
- 객체지향에서 상황에 필요한 객체들의 책임을 중심으로 시스템을 설계해나가는 방법을 책임주도설계라고 한다.
- 하나의 책임이 하나의 객체가 되고, 책임이 곧 객체의 정체성이 되는것이다.
- 책임주도 설계로 시스템을 설계하면 객체들의 정체성이 명확해진다.
- 높은 응집도와 낮은 결합도를 유지하며, 시스템은 객체들의 협력으로 로직을 진행하게 된다. 
   
   
#### 02) 추상화
   
* 추상화를 도입하지 않았을 때 
	- 차량이 추가될 때마다 User의 init함수 안에 if…else 문이 추가된다. 
```python
class PorscheCar:
    def __init__(self):
        self.speed = 0 
        self._fuel = 0
						
    def accelerate(self):
        self.speed += 3

    def decelerate(self):
        self.speed -= 3
		

class User:
    def __init__(self, car_name: str) -> None:
        if car_name == "morning":
            self.car = MorningCar()
        elif car_name == "porsche":
            self.car = PorscheCar()

    def drive(self):
        self.car.accelerate()

```
   
* 추상화를 도입하였을때
	- 구체적인 객체들로부터 공통점을 생각하여 한 차원 높은 개념을 만들어내는 것을 추상화라고 한다.
 	- 차 라는 추상화된 역할의 구현체들은 해당 추상 클래스를 상속받아 구현할 수 있다. 
```python
from abc import ABC

class Car(ABC):
    @abstractmethod
    def accelerate(self) -> None:
        pass

    @abstractmethod
    def decelerate(self) -> None:
        pass

```
```python
class MorningCar(Car):
    def __init__(self) -> None:
         self.speed = 0 
         self._fuel = 0  
						
    def accelerate(self) -> None:
        self.speed += 1

    def decelerate(self) -> None:
        self.speed -= 1

class PorscheCar(Car):
    def __init__(self) -> None:
        self.speed = 0 
        self._fuel = 0
						
    def accelerate(self) -> None:
        self.speed += 3

    def decelerate(self) -> None:
        self.speed -= 3

```
   
- 사람 입장에서는 구체적인 차량이 아닌 추상적인 차 라는 객체만 알면 된다.
   
```python
class User:
    def __init__(self, car: Car) -> None:
        self.car = car

    def drive(self):
        self.car.accelerate()

```
   
   
#### 03) 다형성
   
```python
# 모닝 차량을 운전하고 싶을 때
user = User(MorningCar())
user.drive()

# 포르쉐 차량을 운전하고 싶을 때
user = User(PorscheCar())
user.drive()

```
- User는 생성자에서 추상 클래스인 Car을 의존하고 있지만, 실제로 User를 사용하는 클라이언트에서는 Car가 아니라 Car를 상속받은 자식 클래스 객체를 파라미터로 넘겨줄 수 있다.
- User의 입장에서 Car가 상황에 따라 그 형태가 달라질 수 있는데, 이러한 특성을 다형성 이라고 ㅎ나다.
- 외부에서 실제로 의존하는 객체를 만들어 넘겨주는 패턴을 의존성 주입(dependency injection)이라고 부른다.
- 추상클래스 혹은 인터페이스로 객체를 상위 타입으로 추상화하고, 그 객체의 하위 타입들은 이러한 상위 타입의 추상 클래스 혹은 인터페이스를 구현하도록 하면, 코드 설계가 전반적으로 유연해져 수정과 확장에 매우 용이해진다. 
   
   
##### OCP (Open-Close Principle)
- OCP는 소프트웨어는 확장에 대해 열려 있어야 하고, 수정에 대해서는 닫혀 있어야 한다는 원칙이다.
- 요구사항이 바뀌어 기존 코드를 변경해야 할 때, 기존 코드를 수정하지 않고 새로운 코드를 추가하는 것이 좋다
   
   
#### 04) 캡슐화
- 캡슐화(encapsulation)는 객체 내부의 데이터나 메서드의 구체적인 로직을 외부에서 모르고 사용해도 문제가 없도록 하는 특성이다. 
   
* 캡슐화를 하지 않은 경우
```python
class MorningCar:
    def __init__(self, fuel: int) -> None:
        self.speed = 0
        self.current_fuel = fuel
        self.max_fuel = 50
        if fuel > self.max_fuel:
            raise Exception(f"최대로 넣을 수 있는 기름은 {max_fuel}L 입니다")
						
    def accelerate(self) -> None:
        if self.current_fuel == 0:
            raise Exception("남아있는 기름이 없습니다")
        self.speed += 1
        self._current_fuel -= 1

    def decelerate(self) -> None:
        if self.current_fuel == 0:
            raise Exception("남아있는 기름이 없습니다")
        self.speed -= 1
        self._current_fuel -= 1

```
```python
# 차량 생성
>>> car = MorningCar(30)

# 차량 주행
>>> car.accelerate()

# 차량에 필요한 기름 주유
>>> car.current_fuel += 50

# 차량의 남은 주유랑을 퍼센트로 확인
>>> f"{car.current_fuel / car.max_fuel * 100} %"

```
- 캡슐화를 사용하지 않은 코드의 경우 메서드의 객체에 직접 접근하여 연산을 하며, 이는 버그에 취약한 코드이다.
- 캡슐화되지 않은 코드는 본인의 책임을 다하고 있지 않고(SRP위반), 추후 코드 변화에도 매우 취약하다.
   
   
* 캡슐화를 활용한 경우
	- 외부에서 이 객체에 필요로 하는 기능을 메서드로 제공하고, 객체의 속성을 직접 수정하거나 가져다 쓰지 않도록 한다.
 	- 객체 밖에서는 이러한 정보나 로직을 알 수 없기 때문에, 이를 정보은닉이라고 부른다. 
```python
class MorningCar:
    def __init__(self, fuel: int) -> None:
        self.speed = 0
        self._current_fuel = fuel  # 비공개형 변수로 바꿉니다.
        self._max_fuel = 50  # 비공개형 변수로 바꿉니다.
        if fuel > self._max_fuel:
            raise Exception(f"최대로 넣을 수 있는 기름은 {max_fuel}L 입니다!")
						
    def accelerate(self) -> None:
        if self._current_fuel == 0:
            raise Exception("남아있는 기름이 없습니다!")
        self.speed += 1
        self._current_fuel -= 1

    def decelerate(self) -> None:
        if self._current_fuel == 0:
            raise Exception("남아있는 기름이 없습니다!")
        self.speed -= 1
        self._current_fuel -= 1
        
    # 차량에 주유할 수 있는 기능을 메서드로 제공하고, 구체적인 로직은 객체 외부에서 몰라도 되도록 메서드 내에 둡니다.
    def refuel(self, fuel: int) -> None:
        if self._current_fuel + fuel > self._max_fuel:
            raise Exception(f"추가로 더 넣을 수 있는 최대 연료는 {self._max_fuel - self._current_fuel}L 입니다!")
        self._current_fuel += fuel
        
    # 차량의 남은 주유랑을 퍼센트로 확인하는 기능을 메서드로 제공합니다.
    def get_current_fuel_percentage(self) -> str:
        return f"{self._current_fuel / self._max_fuel * 100} %" 
```
```python
# 차량 생성
>>> car = MorningCar(30)

# 차량 주행
>>> car.accelerate()

# 차량에 필요한 기름 주유 (예외 발생함)
>>> car.refuel(50)

# 차량의 남은 주유랑을 퍼센트로 확인
>>> car.get_current_fuel_percentage()
```
   
- 최종적으로 MorningCar를 사용하는 클라이언트는 객체 속성에 직접 접근하여 연산할 필요가 없이, 퍼블릭 메서드만을 사용하게 된다.
- 이는 추후 수정에 더 용이한 코드이다. 
   
   
##### Getter, Setter와 캡슐화
- 보통 객체지향언어를 배울때 객체의 인스턴스 변수를 모두 private로 두고, 이를 Getter/Setter 메서드로 접근하는 경우가 많다.
- Getter/Setter 메서드는 캡슐화를 돕는 방법 중 하나이며, 캠슐화 그 자체는 아니다.
- 캡슐화는 객체가 알고 있는 것을 외부에 알리지 않는 것이며, 필요한 경우에 한에 일부를 Getter메소드로 제공하거나 Setter메서드로 변경하는 기능을 제공한다.
- 캡슐화는 Getter/Setter메서드의 존재 여부로 결정되는 것이 아니라, 객체가 외부에서 알아도 되지 않을 내용을 잘 숨기고, 알아야 하는 내용이나 제공하는 행동들을 필요에 맞게 제공하는 행동을 이야기한다. 
   
   
#### 정리
- 객체 지향은 객체들의 책입과 협력으로 이루어진다.
- 추상화를 통해 객체들의 공통 개념을 뽑아내어 한 차원 높은 객체를 만들 수 있다.
	- 객체를 사용하는 입장에서 어떤 역할을 할 객체가 필요한지 생각해보고, 추상화된 객체를 생각하면 된다.
 	- 객체를 추상화한 클래스를 만든 후, 이 클래스를 상속받아 실제 구제척인 책임을 담당하는 객체를 만들 수 있다.
- 다형성으로 코드는 수정과 확장에 유연해진다.
- 캡슐화를 통해 객체 내부의 정보와 구체적인 로직을 외부에 숨길 수 있다.
	- 외부에서는 그저 객체가 제공하는 공개 메서드를 사용하면 된다.
	- 캡슐화로 코드는 수정과 확장에도 유연해진다.

### 06 - 의존성 응집도 결합도
   
#### 01) 의존성
- 객체 A입장에서 객체 B의 존재를 알고 있을 때, 객체 A는 객체 B에 의존성이 있다 라고 한다.
      
#### 정적의존성(컴파일 의존성)
- 코드 레벨에서 객체 A내에서 객체 B에 접근하는 경우
- 코드 레벨에서 직접적으로 두 객체의 의존 관계를 파악할 수 있을 때 정적 의존성이 있다고 한다.
- 아래 코드의 경우 User객체가 DataEngineer객체에 정적 의존성이 있다. 
   
```python
from abc import ABC, abstractmethod

class Job(ABC):
    @abstractmethod
    def do(self) -> None:
        pass

    
class DataEngineer(Job):
     def do(self) -> None:
        print(f"데이터 엔지니어링 관련된 일을 합니다.")
        

class User:
    def __init__(self, name: str, job: DataEngineer) -> None:
        self.name = name
        self.job = job
        
    def work(self) -> None:
        self.job.do()

```
   
#### 동적의존성 (런타임 의존성)
- 코드 레벨에서 의존성이 드러나지는 않지만, 실제 싱행 과정에서 두 객체 간 의존 관계가 있을 때 동적 의존성 관계에 있다고 한다.
- 동적의존성은 코드 레벨이 아닌 실제 실행 환경에서 동적으로 의존 관계를 형성할 수 있는 의존성을 말한다.
- 보통 추상 클래스 혹은 인터페이스 파라미터를 타입으로 두고, 실제로 위 클래스를 생성할 때 구체적인 클래스 인자를 넘겨주는 방식으로 동적 의존성을 구현한다. 
   
```python
from abc import ABC

class Job(ABC):
    def do(self) -> None:
        print(f"{self.work_type} 관련된 일을 합니다.")
    
    
class DataEngineer(Job):
    work_type = "데이터 엔지니어링"
    
    
class ProjectManager(Job):
    work_type = "프로젝트 매니징"
    
    
class User:
    def __init__(self, name: str, job: Job) -> None:
        self.name = name
        self.job = job
        
    def work(self) -> None:
        self.job.do()

```
   
- 위 코드에서 User객체는 Job 객체(인터페이스)에 정적인 의존성이 있으며, DataEnginner에는 의존성이 없다. 
- 하지만 다음처럼 실제 코드가 실행될 때 User에 DataEngineer에 의존성이 있도록 만들어 줄 수 있다. 
   
```bash
>>> user_1 = User(name="grab", job=DataEngineer())  # 여기서 동적으로 의존성을 만들어줍니다.
>>> user_1.work()

"데이터 엔지니어링 관련된 일을 합니다."

```
   
#### TIP 
- 정적 의존성 대상을 고수준 코드로, 동적 의존성 대상을 저수준 코드로 넣어주면 더 유연한 설계가 가능해진다,

#### 응집도
- 객체의 책임에 맞게 속성과 메서드가 유기적으로 결합되어 있는 정도를 응집도라고 한다.
- 객체는 하나의 책임(SRP)을 수행하도록 잘 설계가 되어야 한다.
- 응집도를 높게 코드를 작성한다면, 관련성이 높은 속성과 메서드가 모여있기에 흐름을 읽기 편리해진다.
- 불필요한 속성과 메서드를 줄일 수 있어 탄탄한 코드 작성이 가능해진다. 
   
```python
#응집도가 낮은 경우
class LowCohesion:
    def __init__(self):
        self.a = ...
        self.b = ...
        self.c = ...
    
    def process_a(self):
        print(self.a)
    
    def process_b(self):
        print(self.b)
    
    def process_c(self):
        print(self.c)       

#응집도가 높은 경우
class HighCohesion:
    def __init__(self):
        self.abc = ...
    
    def process_a(self):
        self.abc.process_a()
    
    def process_b(self):
        self.abc.process_b()
    
    def process_c(self):
        self.abc.process_c()

```
   
#### 결합도
- 결합도란 객체가 의존하는 정도(정적 의존성)을 말한다.
- 한 객체가 다른 객체의 정보(속성, 메서드)를 많이 알수록 좋지 않다.
- 객체 지향 설계에서는 객체간의 협력이 필수적이기에 의존 관계를 아예 없애는것은 불가능하며, 결국 결합도를 낮게 유지할 수 있는 방향으로 코드를 작성하는 것이 중요하다.
- 결합도를 낮추기 위해선 캡슐화를 통해 내부 구현 로직을 숨기고 외부러 노출할 메서드를 추상화한다.
- 팩토리패턴, 파샤드패턴과 같은 디자인 패턴을 활용하는 것도 하나의 방법이다. 
   
```python
# (BAD) Developer와 Company의 결합도가 높습니다
class Developer:
    def drink_coffee(self):
        ...
    
    def turn_on_computer(self):
        ...
    
    def open_ide(self):
        ...
    
    ...

class Company:
    def make_work(self):
        developer = Developer()
        print(f"{developer.name}가 일을 시잡합니다!")
        developer.drink_coffee()
        developer.turn_on_computer()
        developer.open_ide()
        ...

# (GOOD) 캡슐화를 통해 결합도를 낮춥니다.
class Developer:
    def develop(self):
        print(f"{self.name}가 일을 시잡합니다!")
        self.drink_coffee()
        self.turn_on_computer()
        self.open_ide()
        ...
    
    def drink_coffee(self):
        ...
    
    def turn_on_computer(self):
        ...
    
    def open_ide(self):
        ...
    
    ...

class Company:
    def make_project(self):
        developer = Developer()
        developer.develop()

```
   
개별 객체에는 책임에 따른 기능들이 충분이 모여있고(높은 응집도),
이런 객체들이 서로 협력하는 과정에서 의존하는 정도를 최소한으로 만드는것(낮은 결합도)이
객체 지향에서 말하는 좋은 설계이다.
